# MARSIR column schedule for BP3, 21 November 2026

## Why

On MI300A the generated BP3 operator is limited by shared memory per element (Beverin 757263:
1.02 / 1.58 / 2.81 ms at 4 / 2 / 1 blocks per CU, same kernel). Today four q^3 buffers are live
at once. The z-march ([marsir_zmarch_bp3_2026-11-21.md](marsir_zmarch_bp3_2026-11-21.md))
lowered that but stayed 1.7-1.9x slower: `u` at the quadrature points stayed a shared cube, the
result accumulated into a shared cube, and the plane steps were small.

## The schedule

The layout of libCEED's shared-memory basis kernels (cuda-shared, hip-shared):

- one thread per (x, y) column of the element; every 3-D step keeps z in the thread, so every
  3-D buffer is touched only at the column of the thread that owns it and stays in that
  thread's registers;
- a contraction along z is done in registers;
- a contraction along x or y goes plane by plane: the thread copies its point of plane z into a
  one-plane buffer in shared memory, then each thread contracts its point from that plane.

```
c1 = B along x of u                     3-D step, z in the thread (u is read from global)
for z < n: c2[:,:,z] = B along y of copy(c1[:,:,z])
uq = B along z of c2;  d2 = D along z of uq            registers
for z < q:
    s = copy(uq[:,:,z])                                one plane in shared memory
    d0 = D along x of s;  d1 = D along y of s
    (dv0, dv1, dv2) = flux(G, d0, d1, d2[:,:,z])
    W[:,:,z] = Dt along x of dv0 + Dt along y of dv1   dv0, dv1 planes in shared memory
    V[:,:,z] = dv2
w = W + Dt along z of V                                registers
c19 = Bt along z of w                                  registers
for z < n: c20[:,:,z] = Bt along y of copy(c19[:,:,z])
for z < n: y[:,:,z]   = Bt along x of copy(c20[:,:,z])
```

The summation order differs from today's kernel (rounding-level agreement); the gates check
against host quadrature.

## Compiler changes

1. `--mir-cellwise-schedule=columns=true` (`--mir-bp-schedule=... columns=true`): a 3-D op keeps
   the dimension of its output's last index in the thread, even when the (x, y) points leave
   threads idle. Off by default.
2. `--mir-fuse-phases`: a phase no longer moves past a loop of phases that writes memory. Before,
   any op with a region was ignored, so a phase after a plane loop could join one before it and
   read the loop's result before the loop ran. No committed kernel changes (the golden check is
   byte-identical); the column form is the first with mergeable phases on both sides of a loop.
3. The operator in the column form is generated by `marsir-mlir/test/bp_columns.py` for now, from
   the emitted BP3; `--mir-warp-per-element=lane-owned` puts the 3-D buffers in registers.

Gate: `marsir-mlir/test/bp_columns_gate.py` (emulator on both targets, p = 3 and 7, and the
gfx942 shared memory and spill).

## Resources (gfx942)

| BP3 | today | columns |
|---|---|---|
| p = 3 | 16 threads per element, 4,000 B shared per element, 66 VGPRs | 32 threads per element, 840 B, 128 VGPRs |
| p = 7 | 64 threads per element, 23,328 B, 86 VGPRs | 128 threads per element (81 busy), 5,328 B, 256 VGPRs |

At p = 7 with 64 threads per element a thread holds two columns: 480 VGPRs, so 128.
No private-memory spill in either. The timing is the open question (kit `kit-columns`).
